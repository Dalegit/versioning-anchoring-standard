Semantic Versioning (SemVer) — Examples & Quiz

Draft v0.1.0 Scope: deterministic commitment + release manifests Anchoring infrastructure: not included

SemVer is mandatory: MAJOR.MINOR.PATCH. It tells implementers whether they can upgrade safely. Below are practical examples and a 10-question expandable quiz.

What MAJOR / MINOR / PATCH means (with concrete examples)

Backward compatibility means: someone using the previous version can keep using it without changing their tooling, parsing, or expectations.

MAJOR (breaking change)
Example: Make release.releasedAtUtc required when it was optional → old manifests fail validation.
Example: Change a field type (number → string) for blockNumber → parsers break.
Example: Rename a stable schema ID (insurance.attestation → insurance.attestation.v2) without compatibility support.
MINOR (new, compatible functionality)
Example: Add optional field release.notes → old tools can ignore it.
Example: Add a new schema entry under artifacts.schemas → existing schemas still valid.
Example: Expand documentation with new sections while keeping prior requirements unchanged.
PATCH (compatible fixes/clarifications)
Example: Fix typos and clarify wording without changing any requirement.
Example: Correct a wrong example hash in docs.
Example: If a manifest entry was wrong, you still publish a new version (append-only). That new release is typically a PATCH (e.g., 1.2.0 → 1.2.1).
Pre-1.0.0 (experimental)
Example: 0.3.0 means “expect churn”. You still increment versions properly, but breaking changes are more tolerated before 1.0.0.
No reuse (ever)
Example: You publish 1.0.0, then regret it. You do NOT replace it and still call it 1.0.0. You mark it deprecated and publish 1.0.1 / 1.1.0 / 2.0.0 depending on the change.

Cheat-sheet: breaks old users → MAJOR • adds new safe stuff → MINOR • fixes/clarifies → PATCH • never reuse numbers

Why SemVer matters (in this system)

  • It tells people whether upgrading is safe.
  • It signals whether tooling must change.
  • It prevents “silent breaking changes”.
  • It strengthens credibility of the registry.

Quick examples

  • 1.4.2 → bugfix only
  • 1.5.0 → new safe feature
  • 2.0.0 → breaking change

Quiz: 10 SemVer Questions (click to reveal answers)

Each question describes a change. Decide whether the next release is MAJOR, MINOR, or PATCH (or a note about pre-1.0.0 / no-reuse).

1) You make an optional manifest field required (old manifests now fail).
What version bump is this?
Answer: MAJOR. This breaks backward compatibility because older manifests that were valid now fail validation.
2) You add a new optional field release.notes.
Old tools can ignore it and still work.
Answer: MINOR. New capability is added in a backward-compatible way.
3) You fix a typo in documentation. No requirement changes.
Just a clarity improvement.
Answer: PATCH. It’s a backward-compatible clarification/fix.
4) You change a field type from number → string in the manifest schema.
Some parsers will fail.
Answer: MAJOR. Changing field types breaks compatibility for existing tooling.
5) You add a new schema artifact entry to artifacts.schemas.
Existing schema IDs remain unchanged.
Answer: MINOR. You’re adding new content without breaking existing consumers.
6) You published 1.2.0 but the manifest accidentally listed the wrong doc hash.
You want to “fix it”. What do you do?
Answer: Publish a new PATCH release (e.g., 1.2.1). You must not edit the existing 1.2.0 entry (append-only). A corrected manifest requires a new version.
7) You rename a stable schema ID used by downstream users, with no compatibility plan.
Tools expect the old ID.
Answer: MAJOR. Renaming stable identifiers breaks downstream assumptions and compatibility.
8) You expand the docs with extra examples, but do not change any MUST/SHOULD requirements.
Only explanation improves.
Answer: PATCH (usually). It’s a clarification. If the expansion adds new optional features or new artifacts, it may be MINOR.
9) You are still in 0.x releases and you make a breaking change.
What’s the expectation?
Answer: It’s allowed, but still version properly. 0.x indicates experimental/unstable, so breaking changes are more tolerated, but versions must still progress and be unique.
10) You withdraw a release and want to “reuse” its version number later.
Is that permitted?
Answer: No. A version number must never be reused. Mark the old release deprecated/withdrawn and publish a new version number.
