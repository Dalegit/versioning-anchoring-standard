How to Verify a Release

Draft v0.1.0 Scope: deterministic commitment + release manifests Anchoring infrastructure: not included

Verification should be possible with only the release manifest JSON and a SHA-256 tool. No trust assumptions. No “just believe the maintainer”.

Reminder: Verification is deterministic: canonicalize the manifest bytes, hash with SHA-256, then compare. Chain anchoring checks are optional and outside the scope of v0.1.0.

Verification Steps

This verifies integrity (exact bytes) and, if anchored, public chronology.

1) Obtain the release manifest JSON
   - Download from the registry/release bundle.

2) Confirm canonicalization rules are applied
   - UTF-8 encoding
   - Keys sorted lexicographically (recursive)
   - Stable formatting (no meaningless whitespace churn)
   - LF line endings
   - Trailing newline policy consistent

3) Compute the manifest hash
   - Compute: SHA-256(canonical manifest bytes)
   - Result is: manifestSha256

4) Compare against the published registry value
   - Your computed manifestSha256 MUST match the registry's manifestSha256.

5) (Optional) Verify on-chain anchor
   - Locate the anchor TxID in a block explorer.
   - Confirm the anchored value equals manifestSha256.
   - Record block number and timestamp for chronology.

Common failure modes

  • Different key ordering (non-canonical JSON).
  • Whitespace or indentation changes that alter bytes.
  • CRLF vs LF line endings.
  • Accidentally hashing the artifact file instead of the manifest.
  • Editing the manifest after anchoring (invalidates the anchor claim).

If hashes don’t match, assume the bytes aren’t the same. That’s the point.

Anchor Verification Detail

Anchoring writes only the manifest hash on-chain. Blockchain metadata stays out of the manifest.

Anchor checks:
- Confirm the on-chain transaction payload contains the exact manifestSha256.
- Confirm the block number recorded in the registry is correct.
- Confirm the block timestamp is consistent with the release timeline.

Rules reminder:
- Only the manifest hash is anchored.
- TxID / block number / timestamp MUST NOT be inserted back into the original manifest JSON.
- Anchor metadata belongs in the registry entry (or a separate anchor record).
