Definitions (Plain English)

Draft v0.1.0 Scope: deterministic commitment + release manifests Anchoring infrastructure: not included

This page defines the words that make this system work. Most confusion comes from mixing up what you hash, what you anchor, and what you publish. Read this once and you’ll stop making 90% of the classic mistakes.

Glossary

Open each term. Keep the definitions boring and precise. Boring is good.

Canonicalization

Canonicalization means converting data into one single, agreed format so everyone produces the exact same bytes before hashing. If two people describe the same JSON but format it differently, they’ll get different hashes unless you canonicalize.

Why it matters
Same meaning ≠ same bytes. Hashing cares about bytes.
Common rules
UTF-8, sorted keys, stable whitespace, LF newlines.
UTF-8

UTF-8 is a standard way to encode text into bytes. Hash functions operate on bytes. If one system uses a different encoding, the byte sequence changes and the hash changes.

Rule: Always hash the UTF-8 bytes of your canonical document.

Bytes

A byte is a number from 0–255. Computers store text and files as sequences of bytes. Hashing works on these sequences, not on “meaning.”

SHA-256

SHA-256 is a cryptographic hash function that turns any byte sequence into a fixed 32-byte (256-bit) output, usually shown as 64 hex characters.

Properties people actually care about
Deterministic (same input → same hash), sensitive (tiny change → totally different hash), hard to fake (collision resistance).
Hash (digest)

A hash (or “digest”) is the output of a hash function. It’s like a fingerprint for the exact bytes of a document. If the document changes, the fingerprint changes.

Manifest

A manifest is a structured document (usually JSON) that describes what a release contains. In this system, the manifest is the thing you canonicalize, hash, and (optionally) anchor.

Key idea: The manifest is the “verification surface.”

Canonical JSON

Canonical JSON means JSON that has been formatted in a deterministic way. Typical rules: sort keys alphabetically (recursively), fixed indentation, normalized newlines (LF), no random spacing.

Warning: Most JSON serializers are not canonical by default.

Registry

A registry is the public index of releases/versions. It lists version numbers, manifest hashes, and anchor receipts. It should be append-only: add new rows, don’t rewrite old ones.

Anchoring (on-chain)

Anchoring means writing a small “commitment” value (usually a hash) into a public system that has its own history (like a blockchain). You do this to demonstrate chronology and integrity.

Rule: Anchor the manifest hash, not the raw private content.

TxID / Transaction ID

A TxID is a unique identifier for a blockchain transaction. If you anchor a hash on-chain, the TxID is your public receipt.

Block / Block timestamp

A block is a bundle of transactions recorded together. Block timestamps are a form of public chronology. They typically demonstrate that something existed no later than that time.

Append-only history

Append-only means you never alter old entries. If something was wrong, you publish a new version that corrects it. This prevents “quiet edits.”

Semantic Versioning (SemVer)

SemVer is the MAJOR.MINOR.PATCH numbering system.

MAJOR
Breaking change (old consumers may fail)
MINOR
New features but backwards compatible
PATCH
Fix/clarification, backwards compatible
Version record vs Registry row

A version record is the manifest itself (the real thing being hashed). A registry row is a pointer to it (version → manifest hash → txid). Registry is the index. Manifest is the substance.

Commitment (hash commitment)

A commitment is a cryptographic “I commit to this content” without revealing it. Publishing the hash commits you to the exact bytes, but reveals nothing useful about them.

Commit → Reveal (optional pattern)

Commit → Reveal means you anchor a commitment hash first (private), then later you can reveal the underlying content and prove it matches. Useful when prompts are sensitive.

“Proof” language (why you hesitate)

Anchoring does not “prove truth.” It demonstrates integrity and chronology. Better phrases: “verifiable commitment”, “cryptographic demonstration”, “tamper-evident record”.

Mental model

  • Manifest = what you hash
  • Hash = what you anchor
  • TxID = your public receipt
  • Registry = published index

Typical mistake

  • Hashing the wrong thing (HTML, raw prompt, random JSON)
  • Not canonicalizing
  • Editing history instead of releasing a new version

Examples (tiny and concrete)

Why canonicalization matters

{
  "b": 2,
  "a": 1
}
{
  "a": 1,
  "b": 2
}

Same meaning. Different key order. Different bytes. Different hash. Canonicalization forces one format.

What gets anchored

  • ✅ manifestSha256
  • ❌ your website HTML
  • ❌ raw prompt text (unless intentionally public)
  • ❌ txid inside the anchored manifest

FAQ

Does anchoring prove when I created something?

It demonstrates the content existed no later than the anchor time (block timestamp). It does not prove the exact creation second.

Does anchoring prove I wrote it?

Not by itself. For authorship, add a digital signature layer (sign the manifest with a private key).

Why not just store the prompt in Git?

Git is great for change tracking, but anchoring adds an independent public chronology layer. Git history can be rewritten unless you enforce strict controls.

Why do we keep TxID out of the manifest?

Because the manifest is what you anchor. If you add TxID after anchoring, you changed the manifest and broke the proof. Store TxID in a separate “receipt” record or registry row.

What if I made a mistake in a release?

You publish a new version that fixes it. You do not rewrite the old one. Append-only history is the point.
