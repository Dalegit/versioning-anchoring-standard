Release Manifest Format

Draft v0.1.0 Scope: deterministic commitment + release manifests Anchoring infrastructure: not included

The release manifest is the canonical JSON document you hash and (optionally) anchor. Its bytes must be deterministic under the canonicalization rules.

Scope note: The manifest defines what is hashed and verified. Anchoring receipts (TxIDs, timestamps, etc.) MUST be stored outside the manifest (e.g., in a registry log or release notes).

Example (baseline structure)

This is the conceptual shape described by the system overview.

{
  "schemaVersion": "1.0",
  "release": {
    "name": "Project / Standard Name",
    "version": "1.0.0",
    "releasedAtUtc": "2026-02-11T00:00:00Z"
  },
  "artifacts": {
    "schemas": [
      { "id": "example.schema", "version": "1.0", "sha256": "..." }
    ],
    "documentation": [
      { "id": "canonicalization_rules", "sha256": "..." }
    ]
  }
}

Determinism reminder

  • UTF-8 encoded JSON
  • Keys sorted lexicographically (recursive)
  • Stable formatting
  • Normalized line endings (LF recommended)
  • No trailing newline unless defined

The manifest is hashed after canonicalization. If your bytes differ, your hash differs.

Required fields

These fields are required to make the manifest meaningful and verifiable.

REQUIRED: schemaVersion
- String identifying the manifest schema version (e.g., "1.0").
- If the manifest structure changes, schemaVersion MUST be updated and versioned.

REQUIRED: release.name
- Human-readable name of the project/standard/protocol being released.

REQUIRED: release.version
- MUST follow SemVer: MAJOR.MINOR.PATCH
- MUST be unique and never reused.

REQUIRED: release.releasedAtUtc
- MUST be UTC in ISO 8601 format.
- Used for registry display and chronology expectations.
- The blockchain anchor may be later than this time, but should not contradict it.

REQUIRED: artifacts
- MUST include the release artifacts to which this release refers.

REQUIRED: artifacts.schemas (if schemas are part of the release bundle)
- List of schema artifacts included in the release.
- Each entry SHOULD include stable identifiers and SHA-256 hashes.

REQUIRED: artifacts.documentation (if docs are part of the release bundle)
- List of documentation artifacts included in the release.
- Each entry SHOULD include stable identifiers and SHA-256 hashes.

Recommended fields (non-breaking additions)

These fields are not mandated by the overview, but are consistent with the discipline: they improve verification without changing the core rules. 

RECOMMENDED: release.notes
- Short description of what changed and why.

RECOMMENDED: artifacts[*].sha256
- SHA-256 hashes for each artifact file.
- This is separate from the manifest hash. The manifest hash commits to the list and the artifact hashes.

RECOMMENDED: source.repository and source.gitCommit
- If source-controlled, include repository reference and commit.
- Useful for reproducibility (but not required for hashing discipline).

RECOMMENDED: registryHints.deprecated
- If a release is superseded, mark it deprecated in the registry (do not rewrite old releases).
