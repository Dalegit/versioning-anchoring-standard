Release Manifest Format

Draft v0.1.0 Scope: deterministic commitment + release manifests Anchoring infrastructure: not included

The release manifest is the canonical JSON document you hash and optionally timestamp. In v0.1.0 the shape is deliberately small: a schema version, release facts, and an ordered list of artifact paths with their SHA-256 hashes.

Scope note: v0.1.0 defines the manifest shape, canonicalization rules, and SHA-256 hashing discipline. Signatures, governance, identity, scoring systems, prediction resolution, and anchoring mechanics are outside the scope of the base standard.

v0.1.0 manifest shape

This is the accepted top-level shape for the v0.1.0 base standard. The artifacts field is an array. Array order is preserved. 

{
  "schemaVersion": "0.1.0",
  "release": {
    "name": "Example Release",
    "version": "1.0.0",
    "releasedAtUtc": "2026-05-01T00:00:00Z"
  },
  "artifacts": [
    {
      "path": "payload.txt",
      "sha256": "<sha256-of-artifact>"
    }
  ]
}

Canonicalization reminder

  • UTF-8 encoded JSON.
  • Object keys sorted lexicographically, recursively.
  • Arrays preserve order.
  • JSON.stringify(..., null, 2)-style formatting.
  • No trailing newline.
  • This is not full RFC 8785 JCS.

The manifest is hashed after canonicalization. If your bytes differ, your hash differs.

Required fields

These fields are required for the v0.1.0 release manifest.

REQUIRED: schemaVersion
- String.
- For this base standard release, use "0.1.0".

REQUIRED: release
- Object containing the release facts.

REQUIRED: release.name
- Human-readable name of the release.

REQUIRED: release.version
- String version for the released thing.
- SHOULD follow SemVer where applicable.

REQUIRED: release.releasedAtUtc
- Manually fixed UTC timestamp in ISO 8601 format.
- Treated as an immutable release fact.
- SHOULD NOT be generated dynamically during builds.

REQUIRED: artifacts
- Array of artifact records.
- Array order is preserved by canonicalization.
- Each entry identifies a released artifact and the SHA-256 hash of that artifact's bytes.

REQUIRED: artifacts[].path
- String path to the artifact within the release bundle.

REQUIRED: artifacts[].sha256
- Lowercase 64-character hexadecimal SHA-256 digest of the artifact bytes.

Manifest hash

The manifest hash is computed from the canonical JSON bytes of the manifest. 

manifestSha256 =
  SHA-256( UTF-8(canonicalJson(manifest)) )

The manifest hash commits to the release facts and to the listed artifact hashes. It is not the same as an individual artifact hash.

Do not add these to the v0.1.0 base manifest

These may belong in later profiles, application records, registry rows, or separate receipt files, but they are not part of the v0.1.0 base manifest shape. 

OUT OF SCOPE FOR THE BASE v0.1.0 MANIFEST:
- signatures
- governance fields
- user identity fields
- scoring systems
- prediction resolution fields
- application-specific registry fields
- blockchain TxIDs
- block numbers
- timestamp receipt metadata
- artifacts.schemas / artifacts.documentation nested groups

Example notes

If a project wants a richer domain-specific record, it should define a separate profile or application record that still obeys the base canonicalization and hashing discipline. The base manifest should stay small, reproducible, and boring.
