Publish a verifiable release in 6 steps

Draft v0.1.0 Scope: deterministic commitment + release manifests Anchoring infrastructure: not included

This page explains the workflow and includes a working local demo: build a canonical manifest, compute deterministic SHA-256, then (optionally) send only the manifest hash to a stub backend to simulate anchoring. No private content on-chain. No magic. Just discipline (and a button).

Guided Release Flow (do this in order)

These are “what to do” steps. The demo below uses the official v0.1.0 manifest schema.

1

Collect your Release Bundle (schemas + docs)

Decide what exactly counts as this release. Keep it stable: the manifest is going to commit to it.

See manifest structure Bundle not uploaded here
2

Choose the version number (SemVer)

Use MAJOR.MINOR.PATCH. Breaking change = MAJOR. New compatible feature = MINOR. Fix/clarification = PATCH.

Read SemVer rules Example: 0.1.0
3

Create the Release Manifest (JSON)

The manifest is the authoritative description of the release. You hash the manifest, not your HTML page, not your feelings.

Manifest example Verification steps
4

Canonicalize the manifest (deterministic bytes)

UTF-8. Keys sorted lexicographically. Stable formatting. Same content → same bytes → same hash.

Canonicalization rules Avoid “same JSON, different hash”
5

Hash the canonical manifest (SHA-256)

Compute: SHA-256(canonical_manifest_bytes) → manifestSha256. That hash is the anchor value.

Output: manifestSha256 Try the hashing demo
6

Anchor and publish the registry entry

Anchor only the hash. Keep TxID/block metadata out of the manifest. Publish Version • Hash • TxID in an append-only registry.

See registry (below) Append-only history

  • No TxID/block info inside the manifest.

How to verify (high level)

      

        Verification should be possible with only the manifest JSON and a SHA-256 tool.
      


      

        


1) Obtain the release manifest JSON.
2) Canonicalize it (UTF-8, sorted keys, stable formatting).
3) Compute: SHA-256(canonical manifest bytes) => manifestSha256
4) Compare to the published manifestSha256 in the registry.
5) If anchored: verify the anchor payload corresponds to manifestSha256 and confirm timestamps.
