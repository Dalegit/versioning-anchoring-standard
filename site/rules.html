Rules (Minute Detail)

Draft v0.1.0 Scope: deterministic commitment + release manifests Anchoring infrastructure: not included

These rules define how to publish verifiable protocol releases using deterministic JSON manifests, SHA-256 hashing, and optional public blockchain anchoring. The goal is independent verification without trust assumptions.

1) Core Principles

A release is valid under this standard only if all core principles are satisfied.

1.1 Explicit Versioning
- Every release MUST be assigned a version using Semantic Versioning (MAJOR.MINOR.PATCH).

1.2 Canonical Manifest
- Every release MUST be represented by a canonical JSON "release manifest".
- The manifest is the authoritative representation of the release for hashing and verification.

1.3 SHA-256 Hashing
- The manifest MUST be canonicalized then hashed using SHA-256 prior to anchoring or publication.
- The resulting hash is referred to as: manifestSha256.

1.4 Immutability After Anchoring
- The manifest MUST NEVER be modified after it has been anchored.
- If any change is required, a new release version MUST be issued.

1.5 Append-only Release History
- Release history MUST be append-only.
- Previous versions MUST NEVER be rewritten, replaced, or silently edited.

Summary: version it, manifest it, canonicalize it, hash it, optionally anchor it, and never rewrite history.

Definitions

  • Release Bundle: The set of schemas + docs published as a release.
  • Release Manifest: Canonical JSON describing the release (what it is).
  • manifestSha256: SHA-256 hash of the canonical manifest bytes.
  • Anchoring: Writing only manifestSha256 on-chain to establish public chronology.

Non-goals

  • Does not assert the content is “true”.
  • Does not publish private data on-chain.
  • Does not require a single vendor to verify.

2) Semantic Versioning Rules (MAJOR.MINOR.PATCH)

SemVer is mandatory. Version numbers are part of the verification surface.

2.1 Version Format
- Versions MUST be expressed as: MAJOR.MINOR.PATCH

2.2 MAJOR
- MAJOR MUST be incremented when backward compatibility is broken.
- Examples:
  - Breaking schema field requirements
  - Renaming stable artifact IDs without compatibility support
  - Removing fields that downstream users rely on

2.3 MINOR
- MINOR MUST be incremented when new backward-compatible functionality is added.
- Examples:
  - Adding optional fields
  - Adding new schemas or docs without breaking existing ones
  - Expanding documentation while keeping previous meaning intact

2.4 PATCH
- PATCH MUST be incremented when backward-compatible fixes or clarifications are made.
- Examples:
  - Typos, wording clarifications
  - Non-breaking documentation corrections
  - Correcting a manifest entry without changing the core contract (requires new release)

2.5 Pre-1.0.0
- Versions below 1.0.0 indicate experimental or unstable releases.
- Breaking changes may occur more frequently before 1.0.0, but version numbers must still progress.

2.6 No Reuse
- A version number MUST NEVER be reused, even if the release is withdrawn.
- If a release is invalidated, the registry should mark it as deprecated rather than rewriting history.

3) Canonicalization Requirements (Deterministic Manifest Bytes)

Canonicalization exists to prevent “same content, different hash” failures across OS, editors, and tooling.

v0.1.0 canonical JSON: UTF-8, recursive lexicographic key sorting, JSON serialization with 2-space indentation, LF ( ) line endings, and no trailing newline. (This is not full RFC 8785 JCS; alignment is a planned extension.) 
3.1 Encoding
- Manifest JSON MUST be UTF-8 encoded.

3.2 Key Order
- All object keys MUST be sorted lexicographically.
- Sorting MUST be applied recursively for nested objects.

3.3 Stable Formatting
- Stable formatting MUST be used.
- Avoid insignificant whitespace changes that would alter bytes without altering meaning.

3.4 Line Endings
- Line endings MUST be normalized.
- LF ("\n") MUST be used.

3.5 Trailing Newline
- No trailing newline unless explicitly defined by canonicalization rules.
- If a trailing newline policy is adopted, it MUST be consistently applied.

3.6 Determinism Requirement
- Two independent implementations MUST be able to produce identical canonical bytes for the same manifest content.
- Verification depends on determinism.

Tip: a manifest is not “whatever your browser exported”. It is a deterministic byte sequence.

4) Anchoring Rules (Public Blockchain Chronology)

Anchoring is optional but recommended for public chronology. Only the hash is anchored.

4.1 Anchored Value
- The anchored value MUST be the SHA-256 hash of the canonical manifest: manifestSha256

4.2 On-chain Data Minimization
- Only the manifest hash is written to the blockchain.
- Private release content is not published on-chain.

4.3 No Metadata Injection
- Blockchain metadata (TxID, block number, timestamp) MUST NOT be inserted back into the original manifest.
- The manifest remains immutable once hashed/anchored.
- Metadata belongs in the registry entry, not inside the anchored manifest bytes.

4.4 Multi-network Anchoring
- Multiple anchors on different networks are permitted for the same manifestSha256.
- Each anchor record MUST reference the exact manifestSha256.

4.5 Anchor Record Integrity
- Anchor records MUST record, at minimum:
  - network name
  - transaction ID
  - block number (if applicable)
  - the anchored value (manifestSha256)

5) Governance & Integrity

This governs reference implementations and how forks/third-parties represent themselves.

5.1 Reference Implementation
- An "official reference implementation" may be maintained under a specific name/organization.

5.2 Forks and Implementations
- Forks may implement the standard.
- Forks MUST NOT represent themselves as the official reference implementation without permission.

5.3 Public Verifiability
- Release records MUST remain publicly verifiable.
- The registry should provide sufficient information for independent verification.

5.4 Discipline Over Velocity
- Discipline and transparency are prioritized over feature velocity.
- The system is intended to be credible, not trendy.
